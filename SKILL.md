# Mint Report Creative PPT

Create a readable, source-complete first draft that people can edit in PowerPoint. This is a separate Skill and repository; never modify, install over, or silently invoke `mint-report-ppt`, `mint-report-html` or `mint-report-deck`.

## Workflow

Resolve new/rebuild/edit style authority using [creative-authoring.md](references/creative-authoring.md) before building. Rebuilding with the current Skill uses the current template by default, not historical deck styling. Ordinary body titles are single-line concise summaries; rewrite faithfully instead of shrinking. The shared shell fixes background/title/brand/page fields only, never body topology.

1. Choose the workflow. A task card is optional, including for multi-owner work. If the report order and assignments are already fixed and every owner receives the same outline, Skill version, template and an explicit chapter list, work directly without a card. Use the simple card in [team-workflow.md](references/team-workflow.md) only when a persistent coordination checklist is useful for changing assignments, ambiguous source scope, many contributors, automated scope resolution or merge auditing; it never controls page count or layout. Outline plus owner mapping is sufficient card input: infer order and titles, default the report title when absent, treat the supplied outline as a valid inline source, and do not require audience, purpose, objective or file paths. Ask only when the outline is missing or an owner cannot be mapped uniquely. If the request is task-card-only, generate no PPT or HTML.
2. Read the user's materials completely. Use the copied canonical source adapter before planning. Keep business facts separate from prompt/style instructions; clarify genuinely ambiguous source scope. In the recommended team process, the writer first asks AI outside this Skill to draft a detailed Director Prompt and confirms it. The Skill consumes that prompt as strong design intent. A short prompt remains supported, but no separate hidden Prompt Optimizer Agent is created.
3. In the existing authoring context, complete the director brief and human presentation copy before building. Read [director.md](references/director.md). A short user prompt must still produce a concrete purpose, first focus, relationship design and complete story.
4. Use the available **Presentations** Skill and its documented `@oai/artifact-tool` native API directly. Read [creative-authoring.md](references/creative-authoring.md) and the installed Presentations instructions. Import [the cleaned native Mint template](assets/mint-ppt-16x9-template.pptx) and duplicate its clean base slide; do not start team deliverables with `Presentation.create()`. Author one chapter build script in the private task workspace. You may choose coordinates, unequal proportions and object internals there. No required Slide IR, Scene Grammar, Primitive registry, Composition classifier, or HTML-to-PPT pipeline. Do not edit installed runtime files.
5. Use [the brand contract](assets/brand-contract.json) for fonts, readable size floors, semantic colors and 16:9 dimensions. The template is a visual grammar, not a finite library of page templates. When no sample matches, compose new editable native shapes, charts, tables or diagrams in the same typography, color, line, radius, spacing and hierarchy language. Do not enumerate every future diagram in this Skill. Director composition is a recommendation: the design Agent may adopt a genuinely better measured layout while preserving the page goal, information hierarchy, visual tasks and explicit hard requirements. Record the reason without rewriting the original brief.
6. Finalize with the copied checks and existing Presentations finalizer. Preserve the original native theme/master and the automatic slide-number field on every slide. Bind sources to actual native object names, not to blank containers or hidden metadata. Run [quality-gates.md](references/quality-gates.md); render the actual exported PPT and get independent visual/content review. Technical pass is not visual pass. One targeted repair batch is normal; recheck modified content and affected neighbors. If still failing, identify the blocker and show an explicitly unaccepted candidate only when requested.
7. Deliver the editable PPT, not the private source ledger, code or internal review files. User edits make the current PPT authoritative. Manual Mac/Windows PowerPoint merge is fine; no Agent merge is mandatory. Optional style review and final read-only HTML are in [workflow.md](references/workflow.md).

## Hard contracts

- All supplied business facts belong in readable body content. Preserve subjects, numbers, units, time, forecast/actual state, scope, conditions, uncertainty and relationship direction. No appendix, notes-only substitution or unapproved omission. Evidence IDs and matching bytes alone never establish readable coverage.
- Copy is for leaders: human titles, concise supported prose, exact metrics and nearby conditions. No pipe-separated metadata, schema fields, design keywords or filler. English is for proper names, needed terminology or explicit user direction. Completeness is semantic, not verbatim; reviewed reformulation may not delete unique facts.
- Organize complete management stories. Outline ownership/order does not force page boundaries. Keep related evidence, risk and action together; do not split one sentence per slide or create a context-only empty page. Explicit single-page requirements remain hard. Before unavoidable continuation, retain actual failed full-layout alternatives and the natural break; local overflow alone is not proof. Never fix capacity by shrinking below the contract, stretching short tables or inserting filler.
- Tables/charts/editable relationship diagrams remain native. Preserve precise data, hierarchy and all series. A chart is optional evidence, not a compulsory large visual. A source image may remain an embedded image, but all business fine text needs readable treatment; enlarge, partition or transcribe without losing detail. Never rasterize the whole designed report page.
- Keep genuine parallel, conditional and dependent relations. Use native connectors where there is an actual edge; parallelism may be shown spatially rather than by inventing arrows. Unsupported native behavior is a disclosed limitation, never silently replaced by an unrelated chart/table.
- Keep body/table/chart/edge font floors. Set actual point sizes explicitly; do not confuse native CSS pixels, points and the 1920px review rendering. Disable auto-shrink. Backgrounds may overlap text intentionally; text collisions, occlusion, broken words/ranges and unreadable images fail review.
- One fact has a primary visible presentation. Repetition is allowed only for a different purpose such as a conclusion or calculation; multiple different facts in one raw paragraph are not automatically duplicates.
- The shared master controls brand identity, not content topology. No missing template example is permission to change the business expression, force a generic table/card grid, or paste a rasterized page. New compositions must remain native, editable and visually compatible with the template.
- Do not add a generic bottom source, scope or explanation strip. Place a business-critical condition or boundary next to the evidence it qualifies. The automatic page-number field is the only default footer element.
- Render and inspect each native page and the chapter sequence. Verify first focus, body proof, relationships, word wrapping, hierarchy, meaningful density, color contrast, natural tables and merge/split necessity. A large empty region is not justified by a generic sentence about whitespace. Sources/brief/actual PPT are review inputs, not the generator's defense.
- Current experimental release does not promise mentor-level results or Windows acceptance. Record actual model/runtime/code hash, elapsed planning/build/review/repair time, page count and incomplete checks. Do not expose business material or host session logs in public repositories.
